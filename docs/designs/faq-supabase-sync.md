## Problem Statement

Zwei Fliegen, eine Klappe: Die FAQs von chamaeleon-reisen.de/Infos sollen, wie die
Sitemap, automatisch in den Bot gesynct und in Supabase gelagert werden. Langfristig
sollen Mitarbeiter die FAQs selbst pflegen, ohne Entwickler und ohne git.

## Demand Evidence

Gemessen am 2026-10-07, live /Infos gegen faqs/allgemein.md:
- Etwa 27 der 41 Website-FAQs fehlen dem Bot ganz, z.B. Modifly (vom Owner genannt),
  Vorausbuchung, Abflughafen ab 200 €, Notfallnummer, Chamäleon Club, Trinkgeld.
- Direkte Widersprüche: Gutschein (Bot: Mail mit Gutscheinnummer; Website: Code in
  Schritt 2 der Buchung), Sitzplätze (Bot: Mail; Website: ab 20 €, beim Online-Check-in
  kostenlos, Modifly), BCRT-Adresse (Bot www.bcrt.de; Website www.bctropen.de),
  Einreise-Ort auf der Reiseseite.
- Die Website schickt Gäste ausdrücklich zu „unserem Chatbot Leon“, der dann der Seite
  widerspricht.
- Ursache: allgemein.md steht wörtlich im System-Prompt; /Infos ist nur eine
  nachrangige Ausweichquelle („Falls dir diese FAQs nicht ausreichen…“,
  agent_base.py:1222).

## Status Quo

„Beides“: Service-Mitarbeiter schicken dem Entwickler Änderungen per Mail, er pflegt
faqs/allgemein.md von Hand (13/13 Commits seit April von ihm), und der Bot läuft der
Website hinterher, ohne dass es jemand merkt.

## Target User & Narrowest Wedge

- Website-FAQ: pflegt die Website-Redaktion im CMS. Der Bot zieht nur.
- Bot-eigene Antworten (Ebola-Sprachregelung, Kerosin, Hauptbucher, Jeep, Just4You,
  Provision): kommen vom Service. Das sind „verschiedene Leute“.
- Wedge: „Nur Sync, kein Editor“. V1 hat keine Mitarbeiter-UI.

## Constraints

- „Jetzt nichts löschen, ohne mich zu fragen.“ Keine automatische Löschung von
  Bot-Antworten; Überschneidungen werden vorgelegt, der Owner entscheidet je Eintrag.
- „Alles deterministisch parsbar machen und speichern.“
- Umfang V1 (Owner): „die website faqs im sync und unsere faqs im markdown“. Die
  Länder-CSVs und agentur.md bleiben Dateien. Allgemeine_FAQ.csv wird ab dem
  Umstellungs-Push nicht mehr gelesen (der heutige Import-Assert prüft nur, dass jede
  CSV-Frage als Substring irgendwo in allgemein.md vorkommt, nicht Gleichheit mit
  einer F-Zeile); die Datei bleibt liegen, bis der Owner das Löschen
  freigibt.
- Zielbild (Owner): „allgemein.md soll über kurz oder lang ganz weg, dann nur noch in
  Supabase als Frage-Antwort-Paar“.
- Webbot deployt per Push auf main; schlanke MVPs, billige Unit-Tests ok; keine
  Substring-Checks auf den Prompt, nur Verhaltens-Evals; Evals nie löschen.
- Website liefert ISO-8859-1 und Soft-404s (HTTP 200 auf toten Seiten).

## Premises

1. Website-Vorrang: /Infos ist maßgeblich für jede Frage, die sie beantwortet. Bot-
   Einträge zum selben Thema werden aber nicht automatisch entfernt; ein Abgleich legt
   die Paare vor, der Owner entscheidet.
2. Supabase ist der einzige Speicher für Website- und interne FAQs, als
   Frage-Antwort-Zeilen. allgemein.md wird einmal importiert und danach (nach OK des
   Owners) gelöscht. Kein Spiegelbetrieb, nie zwei Quellen zugleich.
3. Fail-open: Ein fehlgeschlagener Sync lässt den Bot unverändert. Schutzschwelle:
   Liefert der Scrape weniger als 80 % der zuletzt aktiven Website-Fragen oder keine
   Akkordeon-Elemente, schreibt er nichts.
4. Länder-CSVs und agentur.md sind nicht in V1.
5. Evals, die an geänderten Antworten hängen, werden nachgezogen, nie gelöscht.

## Approaches Considered

- A: Sitemap-Klon als Text. Website als Markdown-Blob versioniert, allgemein.md bleibt

## Recommended Approach: B, eine Q&A-Tabelle jetzt

### Tabelle (einmal per Hand im Supabase-SQL-Editor, wie sitemap_versions)

```sql
create table faq (
  id          bigint generated always as identity primary key,
  quelle      text not null check (quelle in ('website', 'intern')),
  extern_id   text unique,          -- tos-txtnr der Website, z.B. 'CHA-T-FAQ-55'; null bei intern
  kategorie   text not null,        -- Website: h3 davor ('Vor der Reise'); intern: '## …' aus allgemein.md
  frage       text not null,
  antwort     text not null,        -- Markdown
  position    int  not null,        -- Reihenfolge im Prompt
  aktiv       boolean not null default true,
  updated_at  timestamptz not null default now()
);
create table faq_history (like faq);  -- plus geaendert_am timestamptz default now()
-- Trigger: before update or delete on faq → alte Zeile in faq_history.
alter table faq enable row level security;          -- nur Service-Role, wie sitemap_versions
alter table faq_history enable row level security;
```

Historie per Postgres-Trigger statt App-Code: Jede Änderung, auch von Hand im Table
Editor, landet automatisch in faq_history.

### Module (Muster: sitemap_sync.py + sitemap_store.py, eine Datei)

- `faq_sync.py`
  - `scrape_infos(html) -> list[dict]`: reine Funktion. Jedes
    `li[tos-template=text_akkordeon]` liefert extern_id (`tos-txtnr`), frage
    (`h4.uk-accordion-title`), antwort (`.uk-accordion-content`, Links als Markdown,
    damit /Infos-Links und bahn.de usw. erhalten bleiben), kategorie (nächstes `h3`
    davor). Decode ISO-8859-1. Unit-Test gegen gespeicherte Fixture
    `tests/fixtures/infos.html`.
  - `scrape_infos` bricht mit Fehler ab, wenn eine `tos-txtnr` doppelt vorkommt
    (sonst scheitert der Upsert-Batch an „ON CONFLICT … cannot affect row a second
    time“). Fixture-Test deckt das ab.
  - `sync(force=False)`: Scrape → Schwelle prüfen → Upsert auf extern_id → fehlende
    Website-IDs `aktiv=false` → Bot neu laden. Fehler loggen, Bot unverändert lassen.
    - Schwelle: abbrechen, wenn keine Akkordeon-Elemente, weniger als 20 Fragen
      (gilt auch beim ersten Lauf ohne Vorgänger) oder weniger als 80 % der zuletzt
      aktiven Website-Fragen. `force=True` überspringt nur die 80-%-Regel.
    - Upsert-Regel: Jede gescrapte extern_id wird `aktiv=true` (eine verschwundene und
      wiederkehrende FAQ lebt also wieder auf). Eine Zeile gilt als geändert, wenn sich
      frage, antwort, kategorie, position oder aktiv unterscheidet; nur dann wird sie
      geschrieben, mit `updated_at=now()`. Unveränderte Zeilen werden nicht angefasst,
      also kein Rauschen in faq_history.
  - Sichtbarkeit: Das Ergebnis des letzten Laufs (Zeitpunkt, ok/abgebrochen, Grund,
    Zahl neu/geändert/deaktiviert) liegt im Speicher und erscheint im bestehenden
    /admin neben dem Sitemap-Verlauf. `POST /admin/faq-sync` (auth_required, wie
    `reindex_travels`) startet einen Lauf, `?force=1` für eine gewollte große
    Umstrukturierung. Ein dauerhaft blockierter Sync ist damit beim nächsten
    Admin-Blick sichtbar.
  - `load()`: aktive Zeilen holen und den Prompt-Block rendern. Website-Block zuerst
    unter „maßgeblich“, dann intern; eine Zeile „Bei Widerspruch gilt die Website“.
    Null aktive intern-Zeilen, ein Fehler oder ein leeres Ergebnis zählen wie
    „Supabase nicht erreichbar“ und führen zum Snapshot.
  - Prompt zur Laufzeit: Heute brennt das f-String `system_prompt_template`
    (agent_base.py:1112) `{allgemeine_faqs}` beim Import ein, eine spätere Zuweisung
    käme nie im Prompt an. Deshalb wird der Platzhalter zu `{{allgemeine_faqs}}`
    (wie `{{kunden_modus_block}}`) und `format_system_prompt` setzt den aktuell
    geladenen Block bei jedem Chat ein. Verhaltens-Eval: Zeile ändern, `load()`
    aufrufen, ohne Neustart fragen, die neue Antwort kommt.
  - Scheduler: als zweiter Job im bestehenden BackgroundScheduler (02:05).
- `scripts/faq_import.py` (einmalig): parst allgemein.md (`## Kategorie`, `**F: …**`,
  `A: …` bis zur nächsten F-Zeile, mehrere Absätze und Listen verlustfrei) in
  intern-Zeilen. Prüft Rundlauf: render(import(md)) ergibt inhaltsgleich die Datei,
  sonst Abbruch.
- `scripts/faq_abgleich.py` (einmalig, read-only): stellt interne und Website-Fragen
  mit difflib-Ähnlichkeit gegenüber, gibt beide Antworten nebeneinander aus. Der Owner
  entscheidet je Paar: intern behalten, intern aktiv=false oder als Zusatzfrage
  umformulieren.

### Kaltstart ohne Supabase

Der Bot darf nicht ohne FAQs starten. `faqs/snapshot.json` wird von
`faq_import.py`/einem Export-Befehl erzeugt und committet, und nur gelesen, wenn
Supabase beim Start nicht antwortet. Er ist ausdrücklich keine Quelle, die Pflege läuft
nie über ihn. ponytail: Snapshot driftet; regelmäßiger Export erst, wenn ein Ausfall
das zeigt.

### Was passiert mit den Abhängigen

- `agent_base.allgemeine_faqs` wird zu einem Wert, den `faq_sync.load()` setzt (wie
  `apply_sitemap`). Der System-Prompt-Platzhalter bleibt.
- `Allgemeine_FAQ.csv` hat heute ein Import-Assert `q in allgemeine_faqs` und baut
  `general_faq_data`, das `chat_quality.faq_corpus()` und `tests/test_faq.py`
  (`EXPECTED_KEYWORDS_GENERAL_FAQ`, `test_allgemeine_fragen_gibt_es_noch`) speist. Ab
  dem Umstellungs-Push: Assert und CSV-Lesen entfallen; `general_faq_data` wird
  `{frage: antwort}` aller geladenen aktiven Zeilen, website und intern. Dass
  `faq_corpus()` damit von etwa 23 CSV-Fragen auf alle aktiven FAQs wächst, ist
  gewollt: Eine Frage, die die Website beantwortet, ist keine FAQ-Lücke.
- Eval-Schlüssel ohne Verlust:
  - `faq_import.py` prüft exakte Gleichheit: Jeder Schlüssel aus
    `EXPECTED_KEYWORDS_GENERAL_FAQ` muss genau einer importierten frage entsprechen,
    sonst Abbruch mit Liste. Bekannte Abweichungen heute: „Versicherungsangebot“ und
    „Versicherungsbedingungen“ (stehen nur im Antworttext, sind keine F-Zeilen) sowie
    „Mein gewünschter Termin ist online nicht mehr sichtbar“ (in allgemein.md mit
    Punkt). Je Fall legt der Owner fest, ob der Eval-Schlüssel oder der Fragetext
    angeglichen wird. Kein Eval wird gelöscht.
  - Setzt der Owner im Abgleich eine intern-Zeile auf `aktiv=false` (z.B. Gutschein),
    wird ihr Eval-Schlüssel im selben Commit auf die passende Website-frage umgehängt
    und die erwarteten Stichworte auf die Website-Antwort nachgezogen.
    `test_allgemeine_fragen_gibt_es_noch` bleibt so grün, ohne dass ein Schlüssel
    verschwindet.
- `tests/test_faq.py` hat Evals auf Bot-Antworten, die der Website widersprechen
  (Gutschein → „gutscheinnummer“, Sitzplätze). Sie werden nach der Abgleich-
  Entscheidung auf die maßgebliche Antwort nachgezogen, nicht gelöscht.

### Reihenfolge der Einführung (Push auf main deployt sofort)

1. DDL im Supabase-SQL-Editor (faq, faq_history, Trigger).
2. `scripts/faq_import.py` lokal: allgemein.md → intern-Zeilen, Rundlauf-Check muss
   grün sein.
3. Erster Website-Sync lokal (`python faq_sync.py`), dann Snapshot exportieren und
   committen.
4. Erst jetzt den Push mit dem Code, der aus Supabase liest. Ab diesem Push liest kein
   Laufzeitcode mehr faqs/allgemein.md oder Allgemeine_FAQ.csv.
5. Abgleich-Skript laufen lassen, Owner entscheidet je Paar.
6. allgemein.md und Allgemeine_FAQ.csv löschen, nur nach OK des Owners.

### Prompt-Größe

Der FAQ-Block wächst von 12 KB auf etwa 35 KB. Bewusst akzeptiert; vor und nach dem
Wechsel Latenz und Tokenkosten je Chat messen (Eval-Lauf abwechselnd main/Branch im
selben Zeitfenster, siehe eval-ab-verschraenkt-messen). Kürzen erst, wenn die Messung
es verlangt.

## Open Questions

1. Welche internen Einträge bleiben bei Überschneidung neben der Website-Antwort
   stehen? Entscheidet der Owner nach dem Abgleich-Skript.
2. Wann wird allgemein.md gelöscht: im selben Push wie der Import oder nach einer Woche
   Parallelbeobachtung (Datei ungenutzt im Repo)? Owner fragen.
3. Wie umfangreich sind Website-Antworten mit Links und Listen im Markdown? Die Fixture
   entscheidet; Ziel ist, dass Links erhalten bleiben.
4. Editor für Mitarbeiter (V2): Der Supabase Table Editor reicht nur für den Owner,
   denn Dashboard-Zugang heißt Zugriff auf die Chat-Logs. V2 ist eine /admin-Seite mit
   Basic Auth wie die Sitemap-Kuration, nur für quelle='intern'.

## Success Criteria

- Leon antwortet zu Gutschein, Sitzplätzen und Modifly wie /Infos (Evals grün, EVAL_N=3).
- Ändert die Redaktion eine Antwort auf /Infos, steht sie am nächsten Morgen in der
  faq-Tabelle und im Prompt, ohne Commit; faq_history zeigt die alte Fassung.
- Ein Scrape einer Fehler- oder Relaunch-Seite ändert nichts (Unit-Test mit
  Soft-404-Fixture).
- Nach dem Umzug liegt keine FAQ-Antwort mehr in git außer im Notfall-Snapshot.

## Dependencies

- Supabase-DDL einmal von Hand (faq, faq_history, Trigger).
- Bestehender Scheduler in sitemap_sync.start_scheduler, db_logging.supabase.

## The Assignment

Bevor eine Zeile Code entsteht: Frag die Website-Redaktion, ob die `tos-txtnr`-IDs der
FAQ-Akkordeons beim Umformulieren oder Verschieben einer Frage gleich bleiben (z.B. mit
CHA-T-FAQ-55, Modifly), und ob dieselbe ID auf /Infos zweimal vorkommen kann. Davon
hängt ab, ob extern_id als Upsert-Schlüssel trägt oder ob
eine umgeschriebene Frage als neue Zeile plus deaktivierte alte ankommt.

### R2-1 — feasibility (blocking)

**Problem**

> The claim that no eval is lost depends on CSV questions being identical to parsed allgemein.md question texts. That is not established.
